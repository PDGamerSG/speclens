Research date: 14 November 2026, Asia/Kolkata. Sources were retrieved on 13 November at 19:12–19:14 UTC (14 November, 00:42–00:44 IST). This bounded follow-up investigates the two additional factory sections, Nonconformances and Activity. It uses opened primary publications and official guidance, with the retrieval record below. No factory interviews, paid model calls or empirical factory performance measurements were made.

Build a small issue register around a specific lot, observable evidence, the affected requirement, a responsible person, immediate containment and a documented resolution. Preserve attributable lifecycle changes alongside it. A status change should help the next person understand what was done and why; it does not establish that a physical batch is safe to release.

## Concrete section behavior

These are bounded implementation proposals for the approved workspace design. Their presence in this note does not certify the full release; software verification is recorded by the implementation's checks.

| Section / job | Approved release scope | Interpretation and possible later extension |
| --- | --- | --- |
| Nonconformances: identify the problem | Team-owned issue with title, severity, lot, optional inspection, description, requirement, root cause, evidence and assignee; statuses open, contained and closed. | Record the relevant clause in requirement and observations in description/evidence. These text fields preserve the team's investigation; the app does not verify cause or effectiveness. Severity is a team's triage label, not a model-estimated safety rating. |
| Nonconformances: contain and resolve | Record immediate containment separately from corrective action and resolution. Closure requires corrective-action and resolution text, with attributable history. | “Contained” records an action taken, such as isolating the identified lot for review. It does not mean released. Resolution should say what was checked, by whom and against what evidence; an action plan in future tense is not proof of implementation. If a substantive corrective action is unwarranted, the text should state the reason and the quality owner's decision rather than fabricate an investigation. |
| Nonconformances: preserve links | Keep the lot/inspection association stable and same-team; preserve original model recommendations and independent human dispositions. | An issue's closure does not approve a memory standard, overwrite a model result or automatically release material. Explicit disposition and standard approval retain their own workflows. A later investigation can consider other affected lots, with evidence before expanding the affected population. |
| Activity: handover and reconstruction | Retained, append-only events for successful workspace lifecycle mutations, actor snapshot, action, target, timestamp and available details; event and record changes commit together. | Show links to the changed object and enough prior/current status context to understand the handover. Ordinary API users cannot rewrite historical events. Administrative deletion/retention remains an explicit separate process. This is not a cryptographically protected log or a complete security audit: denied requests, read access and all infrastructure events are not established as covered. |
| Activity: useful signal | Team-scoped event list with durable links and server-derived attribution. | Filter by target/type/person locally only when the complete relevant history is loaded. Keep image/specification evidence on its own record rather than copying entire sensitive payloads into every event. Later paging/export must make completeness visible. |

A practical first factory exercise is to open an issue from a disputed inspection, assign it, record isolation of the affected lot, capture the responsible person's completed action and resolution, then reconstruct the sequence using Activity and a lot export. Failure to recover the evidence, original decision or accountable actor falsifies the usefulness of the handover. A successful exercise demonstrates workflow traceability, not defect-detection accuracy or regulatory certification.

## Validation implementation boundary

The companion evaluator in `backend/app/pilot/validation.py` accepts **precomputed imported outputs**. It performs no inspection or provider call. The new `/api/workspace/pilot/validation` routes use the same team/session boundary as other factory sections. Admins and engineers may import; active team roles may read. Each saved validation record and its event use the shared repository transaction. Validation runs are separate from production lots/captures and cannot add production part counts.

The import contains `sample_id`, `physical_part_id`, `lot_id`, `session_id`, binary truth, optional severity, and baseline/memory outputs (`good`, `defect`, `uncertain`, `error`). These identifiers are importer-supplied grouping labels; they are not verified links to operational lot records. There is a maximum of 2,000 rows, bounded identifiers and a 12,000-byte configuration object. Configuration is finite JSON with bounded depth and does not control the bootstrap work budget.

The immutable manifest retains all normalized input rows, their order, the selected first sample per physical part, grouping membership, evaluator version and a SHA-256 hash covering manifest and configuration. Duplicate sample IDs are refused. Repeated physical parts must have identical truth, predictions, severity and lot; sessions may differ and connect otherwise separate groups. Input order explicitly declares attempt order. The evaluator cannot discover the actual chronological first attempt from these fields; the importer must supply fixed first-attempt results. Conflicting retake outputs are refused rather than selecting a favorable result.

Every run reports a **two-truth-by-four-output matrix**. Escapes are `truth=defect, output=good` divided by all defective physical parts. False rejects are `truth=good, output=defect` divided by all good physical parts. Review and error workloads divide by all physical parts. Decision coverage counts only binary outputs. A zero denominator produces `null`, not a zero rate. No combined accuracy score treats Review as a correct positive. Paired binary improvements/regressions require both arms to have binary decisions; restored/lost decisions and all four-by-four output transitions are reported separately.

Uncertainty resamples paired **connected lot/session groups**, with parts in the same lot or session kept together, including crossed sessions. It never treats repeated views as independent observations. The 1,000-replicate deterministic percentile bootstrap reports memory-minus-baseline rate differences. Fewer than two groups produces no interval; fewer than ten produces an explicit instability limitation. Replicates lacking the relevant truth class are omitted for that rate and their valid count is reported. A degenerate zero-difference interval does not provide an upper bound on the underlying escape probability. Different labels do not prove independence, representative sampling, correct ground truth, model provenance or absence of teaching/test leakage; these limitations remain explicit even when the importer supplies an optimistic configuration.
