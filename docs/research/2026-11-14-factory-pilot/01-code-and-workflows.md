# SpecLens: code and workflow audit for a real factory pilot

Date: 2026-11-14. Source baseline: `main`, commit `3e39563`. This is a read-only application audit; the only output is this research document. No application changes, deployment changes, live provider calls, secret reads, commits, or pushes were made.

**Recommendation:** turn the existing inspection and correction loop into a controlled, shared pilot workflow. The first release should add named team access, a small approved part/specification catalog, durable lot-linked human review, and an evidence export. Preserve the current viewer, masks, visual memory, batch processing, comparison tooling, dashboard, and stores. Adding another AI inspection feature is less urgent than making the existing decision safe to find, assign, approve, and trace.

## Reading this audit

- **Observed** describes behavior in the source at the baseline commit. Citations are repository-relative `file:line` references; line ranges indicate the relevant implementation block.
- **Partial** means useful code exists but the complete factory workflow does not.
- **Missing** means no relevant entity, route, or UI workflow was found in the inspected application, schemas, and route inventory. This is an application finding, not proof about an external system.
- **Proposal** and **inference** are explicitly labeled below. Proposed files and entity names describe where a later implementation would belong; they do not exist yet.
- The task brief supplied a green baseline of 159 backend tests and 25 Playwright tests. Those suites were not rerun for this document. Existing test names were inspected as supporting evidence, not treated as production accuracy validation.

### Documentation and naming differences that matter

1. `docs/user-guide.md:5` still describes four sections, while the source has five navigation entries plus a batch section (`Workspace.tsx:18-24,234-246`). Its fixed defect-class claim at line 124 is obsolete; classes are dynamic. Its cookie expiry description at line 140 is obsolete; API access renews the cookie (`public.py:180-183`).

## 2. Practical workflows and their gaps

### Quality operator

**Observed workflow:** open settings, type factory/part/spec text, take/upload one photo, inspect with or without memory, read the ticket and outline, inspect again, or save a correction. For several photos, choose a batch and open prioritized results. Photos and resulting inspections persist, and pending memory saves can be retried.

**Factory workflow proposal:** sign in; choose an assigned station and active part/revision; scan or enter the physical lot; follow its capture instructions; capture the required view; submit once; see “captured / analysis pending / awaiting review / reviewed” separately from the model assessment. Request a retake or flag a concern without writing a standard. Continue work and recover unfinished captures after reload. Human material handling continues under the plant's existing disposition procedure during the pilot.

**Concrete gaps:** free text is easy to mistype and can silently create another memory/history scope; no lot/station/capture identifier; no actor-bound confirmation; model recommendations are presented as Accept/Reject while final disposition is not a separate saved action. “Inspect again” creates another inspection with no explicit retake/reinspection relationship. Browser batch state disappears on refresh, although jobs survive. A shared browser cannot establish which operator acted.

**Narrow change locations:** extend `ScopeSettings`/request schemas into a selected server catalog reference; `Workspace.tsx` for selection and capture context; `Ticket.tsx` for assessment versus review status; `workspace/routes.py` for capture submission; `workspace/service.py` for immutable context snapshots. Reuse `PartViewer.tsx`, `photo.ts`, current media validation, and `jobs/`.

### Quality engineer

**Observed workflow:** inspect history or sorted batch results, open a ticket, write one correction/rule, retain to Hindsight, retry pending sync, inspect another part, compare memory on/off, and ask Hindsight to summarize. All synced corrections are eligible for recall. The crop is derived from the original model's detected box; when it had no box, the crop is the whole image (`service.py:129-142`).

**Factory workflow proposal:** open a persistent review inbox; claim a case; inspect photo, model explanation, exact active specification, and recalled sources; record Accept/Reject/Hold/retake with a reason; close the case without changing future model behavior. Separately propose a reusable visual standard with evidence and clause link; an authorized engineer approves its release, checks it on held-aside examples, supersedes a contradictory standard, or retires it. Imported taxonomy remains draft until a person confirms classes, units, clause meanings, and capture assumptions.

**Concrete gaps:** a one-part exception currently becomes a future rule immediately; sync status is mistaken for governance status; no approve/reject/retire actions, reviewer identity, conflict review, standard ownership, or change log. No independent human reference-label/adjudication flow. One immutable correction per inspection is a useful historical constraint but cannot itself represent a full review and standards lifecycle. Reflection currently calls the bank directly (`routes.py:265-267`), so a future retirement feature must govern summaries as well as inspection prompts.

**Narrow change locations:** keep immutable `corrections` as evidence; introduce separate disposition and standard lifecycle records in `db.py` plus Alembic. Put review actions in proposed `workspace/review.py` and standard governance in proposed `workspace/standards.py`; make `service.run` admit only active approved standard sources. Extend `StandardsSection` and the correction form, rather than replacing Hindsight.

### Supervisor / pilot owner

**Observed workflow:** switch scope, read trend/Pareto/correction/cost dashboard, search loaded history, and export JSON/CSV. Status/cache/budget are partly server-wide. There is no team-wide overview or lot closure.

**Factory workflow proposal:** see today's captures, pending/aged human reviews, failure backlog, operator/station coverage, and each lot's reviewed count; open the exact cases behind an exception; export a dated lot packet containing assessment, final decision, specification revision, actor, timestamps, and source evidence. For pilot evaluation, compare model outcomes with independently adjudicated labels and report false accepts, false rejects, review load, latency, and missing data with denominators.

**Concrete gaps:** no lot denominator, work-shift context, pending-case age, final decision counts, sampling plan, or review completion measure. Current correction share cannot be interpreted as accuracy: unreviewed errors are invisible, and operators may only correct obvious failures. Current comparisons add two rows to inspection metrics (`service.py:211-213`). One physical item may be uploaded repeatedly. UTC day aggregation (`dashboard.py:40`) may not align with the factory shift or local workday.

**Narrow change locations:** extend the existing `dashboard.py` with explicit production/evaluation modes and reviewed denominators; `Dashboard.tsx` with backlog and lot filters; `sections.tsx`/`api.ts` with server paging and filtering; proposed `workspace/reports.py` with a versioned export schema. Reuse current CSV/JSON mechanics.

### Data design principles for the pilot

**Proposal:** preserve the current content blob/hash as reusable storage, but introduce tenant-owned controlled revision objects above it. A content hash answers “which text?”; a revision object answers “which approved standard applied to this part at this time?”. A display-name change should not move the factory to a different history or Hindsight bank. Scope identity should use stable tenant/part/revision identifiers, with explicit migration/versioning, rather than names plus browser owner.

**Proposal:** keep AI assessment, human disposition, reusable standard, and remote memory-sync status as separate facts. Each has a different actor and lifecycle. Store the active revision, taxonomy snapshot, capture protocol, model identifier, prompt/config version, and approved standard sources used for an assessment. Record whether an entry is production capture, reinspection, comparison arm, or evaluation; otherwise operational counts remain ambiguous.

**Proposal:** retirement must take effect in the local source whitelist immediately, even if Hindsight deletion is pending. A remote recall should never re-enable a retired standard. Review retained crops and generated summaries under the same eligibility rule. Moving to a new revision should start an explicitly approved standards release; do not automatically copy all old corrections.

## 4. Dependency order and the narrow first release

### Dependency order

1. **Choose the pilot boundary and evidence contract.** One factory, one part number/family, one station/capture setup, and a limited set of visible defects. Agree who owns final decisions, what a lot means, how to label reference outcomes, which shift/timezone applies, and how long evidence is retained. Capture representative real photos before promising thresholds or sizes.
2. **Create verified identity and stable tenancy.** Establish named users and shared tenant IDs; add actor IDs and permission checks on API, media, reports, jobs, and standards. Keep demo cookie scopes separate from pilot records. A pilot-specific auth gateway is possible only if the application receives verified user identity and enforces action permissions; network access alone does not supply authorship.
3. **Create a minimal controlled part/spec catalog.** Save one part and its approved revision, human-confirmed taxonomy, capture instructions, and active standards release. Snapshot references at job submission. Block pilot capture against unapproved or retired revisions. Retain content hashes and parsers.
4. **Add capture/lot identity and a durable review inbox.** Carry lot, capture, actor, station, and revision through job submission to inspection records. Add independent dispositions, review case status, reload recovery, and idempotent processing. Queue every pilot assessment for human confirmation at first; later relax based on measured evidence.
5. **Separate and govern teaching.** A disposition can propose a standard, but only approval makes it eligible for future recall. Implement retirement and conflict review before shared rule publication. Existing retain retries remain useful.
6. **Export and evaluate the real pilot.** Add complete server-filtered reports with both AI and human decisions, excluded comparison/evaluation rows, backlog counts, a versioned manifest, and retention rules that preserve active approved standards and required evidence. Run representative held-aside evaluation; only then consider automation or an external integration.

Infrastructure migration is a separate operational decision. A bounded pilot can use the existing Lightsail/SQLite/local-media/inline-job architecture if measured concurrency, backup/restore, uptime, and latency meet the agreed pilot needs. If several processes, higher availability, or recovery targets require another store/worker topology, reuse the existing optional Postgres/R2/external-worker adapters rather than inventing another platform.

### Narrow first release: one controlled inspection lane

**Proposal:** ship the following together as one vertical slice, because each is needed to make the physical evidence attributable and reviewable:

- Named operator and quality engineer access to one shared pilot team; supervisor read access. Use an existing identity service or verified enterprise proxy where practical. Administrative role controls who can activate a revision or publish a standard.
- One durable part, one approved specification revision, confirmed classes/units, and one capture instruction set. No generic catalog import or complex revision diff is needed initially.
- Required lot reference, capture ID, station, actor, timestamp, and revision on every pilot submission, with explicit retake links and an idempotent submit path.
- One durable review list with open/claimed/closed status. Every pilot assessment receives a named human disposition; uncertain cases can be held or sent for a new photo. Existing physical material-release procedure remains the authority.
- A separate “propose reusable standard” action. Engineer approval gates memory publication; retirement removes eligibility immediately. Existing Hindsight sync and crops are reused.
- A lot summary and complete CSV/JSON evidence export with model/human decisions side by side, source image references or agreed bundle, revision and standard sources, actor, timestamps, and missing-evidence counts. Fix history paging at the same boundary.
- An agreed retention/backup policy and a measured pilot dataset containing acceptable parts, relevant defect severities, lighting variation, and retakes. Report false accepts, false rejects, review workload, and latency from independently labeled outcomes.

**Proposed acceptance scenarios:** an operator's capture can be found by another authorized engineer after reload; another tenant cannot obtain its records/media/jobs; inactive users cannot act; a draft/retired revision cannot start a new pilot assessment; a closed human decision never alters the original AI record; closing a case does not automatically teach memory; an unapproved/retired standard never appears in a new prompt; retry/restart cannot silently double-count the same capture; a lot remains reconstructable after job cleanup; a report includes all selected records beyond the first 100 and identifies every missing image or undecided case. These require targeted integration tests when implemented, beyond the existing regression baseline.

**Defer until evidence or a named customer requires them:** autonomous accept/reject/release, conveyor/PLC control, multi-camera fusion, multi-defect segmentation, broad part-family rollout, offline synchronization, native mobile app, full CAPA/NCR workflow, SPC/control charts, supplier portal, generic MES/ERP integrations, billing, and infrastructure migration for its own sake. Existing memory comparison remains an engineer's validation tool rather than the operator's primary navigation destination.

## 5. Risks and unknowns to resolve

| Risk / unknown | Evidence and practical implication | Pilot response proposal |
| --- | --- | --- |
| Real defect performance is unproven | Bundled parts are synthetic; the documented ablation has four cases on two held-aside source photos. Low correction share or high model confidence does not establish a false-accept rate. `README.md:233-235`; `Ticket.tsx:61`. | Assemble representative factory data with independent labels and locked holdout groups; agree severity-dependent acceptance criteria and uncertainty before enabling any automated disposition. |
| Shared standards can be poisoned or contradicted | A self-entered reviewer can immediately retain a future rule; all synced corrections qualify. `CorrectionForm.tsx:16-33`; `service.py:174-192,56-62`. | Authenticated actors, proposal/approval/retirement, conflict review, approved-source whitelist, and a held-aside check before publication. |
| Same text can share a mutable derived taxonomy across visitors | Global hash-keyed taxonomy plus owner-free model extraction. This does not show record leakage, but it permits cross-workspace changes in how identical text is classified. `store.py:91-99`; `routes.py:399-426`. | Tenant-owned revision/reading objects; approved immutable taxonomy snapshots; role-check extraction/activation; scope tests for derived artifacts, not only inspections. |
| Physical part/lot can be lost while inference jobs look healthy | Inspection payload has no lot or batch link; job group is the only batch relationship and can expire in seven days. `service.py:79-87`; `jobs/purge.py:3-4`. | Durable lot/capture relationships independent of job lifecycle; stored batch index/reload workflow where operationally needed. |
| A worker retry can repeat a saved assessment | `run_claimed` invokes the runner before job completion is persisted; `service.run` generates a fresh inspection ID every execution. A crash between those commits can create an extra inspection on recovery. `jobs/queue.py:106-109,128-149`; `service.py:76,88`. This is an inferred crash-window risk, not a reproduced failure. | Stable capture/job idempotency key, transactional result association or lookup, and restart/failure-injection acceptance testing. Keep physical counts distinct from model-call counts. |
| Evidence and active rules can expire together | Purge deletes old corrections and Hindsight documents alongside inspections by age; it has no approved/active exception. `store.py:279-312`; `service.py:262-265`. | Decide evidence retention with the factory; decouple approved standards from operational inspection expiry and retain approved source evidence appropriately. Do not make a 90-day demo default the factory policy accidentally. |
| Measurement can be mistaken for metrology | Millimetres use nominal width divided by a model-generated bounding box, then mask dimensions; source is resized to 1280, model photo to 768. `inspect/measure.py:3-4,23-29`; `service.py:63-68`; `inspector.py:57-58,81`. | Keep it an estimate unless validated against known gauges/fixtures; specify capture pose and scale. If acceptance depends on tiny dimensions, establish imaging resolution, calibration, uncertainty, and a measurement procedure first. |
| Missing masks can still yield Reject | Inspector default requires a mask, but workspace explicitly calls `require_mask=False`; a Reject does not guarantee SAM evidence. `service.py:73-74`; `inspector.py:108-111`. | Decide per-defect evidence requirements; route missing required evidence to human review rather than assume every rejection is measured. Preserve a clear evidence-status field. |
| Report metrics can be misread | Model verdicts drive reject rate; comparison arms count as inspections; “memory cited” counts nonempty recalled sources; no physical-item denominator. `dashboard.py:28-48,60-78`; `service.py:211-213`; `store.py:133`. | Label assessment versus final disposition, separate production/evaluation/reinspection counts, capture denominators and independent labels, and state timezone/shift definitions. |
| Full evidence recovery is not yet a product workflow | Full owner JSON export exists but does not bundle image bytes; browser history export is first-page limited. Image files can be deleted by retention. `routes.py:364-370`; `Workspace.tsx:248-250`; `store.py:264-272`. | Server-filtered full export with manifest, explicit missing-file status, agreed media bundle, and a tested restore/reconstruction exercise. |
| Cloud/availability/data handling assumptions remain unverified for a factory | Live source points to one Lightsail backend, optional alternatives exist, and the repository does not record provider retention terms (`docs/security/threat-model.md:23`). Offline capture synchronization is absent. | Agree photo/IP requirements, provider data handling, connectivity and recovery targets with the pilot owner; test service restart and backup restore. Choose migration/offline work only against those needs. |
| Demo limits can stop normal shift traffic | Public mode limits POSTs to 30/browser/hour and 120/IP/hour, counting most writes including correction/sync/reflect; budget is server-wide. `public.py:20-27,102-105,168-173`; `routes.py:152-157`. | Separate pilot identity/quota policy from the public demo, measure expected station throughput and model/Hindsight costs, and make blocked work visible and recoverable. Do not simply remove all spend controls. |

Unanswered product inputs: actual part and material, defect consequences and minimum observable size, inspection volume/peak concurrency, photo hardware/environment, responsible approver, lot/work-order source, ERP/QMS destination, factory connectivity, language/accessibility needs, applicable records policy, provider/data-location constraints, target detection errors, and acceptable time per reviewed part. These determine the pilot's final acceptance criteria; the source alone cannot settle them.

The highest-value next implementation is the controlled lane above. Its success is that a real operator can submit a real lot item, an authorized engineer can resolve it later, an approved standard can influence only the intended revision, and a supervisor can reconstruct both machine and human decisions from durable evidence.
